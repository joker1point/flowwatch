## 2026-10-16 · 告警规则与界面入口

把「告警规则引擎」与「单端口界面」两条线收尾进仓（提交 `927c406` + `c51decd`）。本节记录**关键决策与被否方案**——维护时请优先尊重这里的取舍理由。

### 1. 界面入口：由「第二个服务」改为「8788 同源挂载」

- **需求**：一个「随时打开界面」的日常入口。
- **被否方案 A（已做出后被否）**：入口拉起 `run.py --port 8791`（第二份服务 + 第二份采集器 + 新浏览器窗口）。
  **否决原因**：在内存紧张的机器上（实测可用仅 2.5 GB / 7.9%）打开即引发系统卡顿——「零新增进程」是这类机器的硬约束；库写入虽然是 `ON CONFLICT DO UPDATE`（覆盖语义、不会翻倍），也救不了服务+采集双份的常驻成本。
- **被否方案 B**：轻量静态服务器托管 `web/dist`。**否决原因**：单端口构建的 API 基址是同源 `/`，静态服务无法提供 `/api`，前端整页 404。
- **定案**：`server.py` 在 `web/dist/index.html` 存在时**同源挂载**（挂在所有 `/api` 路由之后，不会遮蔽 API）→ **常驻的 8788 本身就是界面**。桌面入口只做两件事：8788 在跑 → 秒开浏览器（零新增）；没跑 → 最小化拉起再开。
- **对开源用户同样成立**：默认构建（`VITE_API_BASE=/`）与开发构建（前端指向 127.0.0.1:8788）在 8788 上请求的都是同源 `/api`。8791（run.py）作为一键包/演示包入口**不变**。

### 2. 告警种子规则：由「代理进程列表」改为「% 全机兜底」

- **原设计**：默认规则以 `%flclash% / %mihomo% / %clash%` 匹配代理内核（sentinel 的等价保护）。
- **改因**：① **品牌边界**——开源产品的 UI 文案 / 默认配置 / 示例数据一律按对外材料处理，不点名任何具体客户端（含同类内核名）；② 事故形态的本质是「大流量上行」，与是不是代理无关；③ 对开源用户开箱即用。
- **定案**：「大流量上传（通用保护）」进程匹配 `%`（所有进程）· 60 min 上行 ≥ 10 GB（或 30 min ≥ 5 GB）· 默认开；「持续传输提醒（全机）」`%` · 连续 ≥ 60 min · **默认关**（常开代理/网盘的机器会周期性触发）。
- **取舍（明示）**：失去「精确只盯代理」的针对性——个性化需求走面板（一键模板 + 从最近进程点选，同批交付）。
- **边界（易踩）**：种子**只在规则文件「无规则」时**种入；手动清空 `rules` 数组**不会**重种（要重启后端）。**测试残留规则会占位挡住种子**（10-16 实例：一条测试规则挡了两天，且一直在被评估）。

### 3. 告警面板降门槛：模板 + 点选（纯前端）

- **动机**：原表单对非技术用户门槛高（要会 LIKE 通配、要懂流量概念、要自己选阈值）。
- **定案**：一键模板（大流量上传 / 大流量下载 / 持续传输）+ 进程点选（`/api/history/top` 近 24h 有流量的进程，点击即填）+ 术语通俗化；**不动后端**。
- **有意未做**：多步向导；模板只覆盖最高频的三类。

### 4. 品牌清洗的范围与验证口径

- 清洗落点：`alert_rules.py`（种子 + 文档串）、`AlertRulesPanel.tsx`（占位符）、`tests/test_alert_rules.py`（夹具）、`scripts/proxy_sentinel.py`（退役时一并泛化；**历史提交里的具名不动**）。
- **验证口径：打在构建产物上**（`dist/assets/*.js` 扫描 0 命中），不只扫源码。清洗脚本 `_deploy/flowwatch/cleanup_brand.py`（可重跑、带自检）。

### 5. 提交范围：功能组 + 排除本机产物

- 前端面板与后端引擎互相引用，**不可拆半提交**（只提前端会让仓库处于引用不存在后端的状态）。
- 不入仓：`resident.cmd`（autostart.py 生成、含本机路径）、`alert_rules.json`（运行时数据）→ 已进 `.gitignore`；一次性诊断脚本（`diagnose_*` / `find_chatgpt*` 等）留本地。
- 过程记录：远端已有 README 提交 → `pull --rebase` 后推送（无冲突）。
