## 1. 候选集窄化（注入给模型的工具从 12 → 2~4）—— 状态：`计划中`

**目标**：提高"该调工具时真去调"的比例，同时降低选错工具与 token 开销。**不改能力边界**，只改"注入给模型的清单"。

**背景（为什么值得做）**

- 现在每轮全量注入：聚合档 11 个 / 明细档 12 个。相近工具多（`get_top_processes` /
  `get_process_history` / `get_process_identity` 最易混），选择空间大；
- 工具 schema 带长描述（单是 `get_top_processes` 的描述就 200+ 字），每轮都在烧 token 与注意力；
- 与"隐私分档"同构：分档 = 该档不给的工具**不注入**；窄化 = 该**问题类型**用不到的工具不注入。

**设计要点**

1. 规则表**复用 `_fallback_picks`**（系统侧补查那套"问题类型 → 工具"映射），不新造第二套，
   避免两处词表漂移（09-22 已经吃过一次"两个词表不一致"的亏）；
2. 触发条件：`needs_data` 为真时窄化；概念问答 / 记忆请求保持全集（避免削弱表达力）；
3. **只改注入、不改可执行**：`run_tool` 的档位硬闸不动，"窄化没给的工具"**不拒绝执行** ——
   窄化是提示优化而不是能力边界；否则模型第二轮真需要别的工具时会被自己卡死，
   且规则表一旦窄错，整轮直接废；
4. 保守优先：候选宁多勿少（建议上限 4），并保证**兜底工具**（`get_live_frame` / `get_health`）
   总在候选里；模型明确说"需要 X 能力"时，放开一组重问一次（复用纠正轮机制）；
5. 记忆工具默认保留（读的 `conversation_search` 一定留）；**写记忆的三个是否只在记忆请求时
   注入 = 与本项解耦的独立问题**，见 §2。

**验收判据**

- 新增评估集判据 `offered_tools_max`（候选数上限）+ 至少 1 条用例钉住"窄化真的生效"；
- 现有 3 条 `offered_tools_all_of` 用例（分档、事件、身份）同步调整；
- **live 前后对照四个数**：零工具调用率 / 首轮调对率 / 平均模型往返次数 / prompt token 数
  —— `done` 已有 `tools` / `retried` / `grounded`，需补一个"本轮候选数"字段才能量。

**风险**

- 窄错 → 模型要么如实说"我没这个能力"（差体验），要么拿别的工具凑（更差）。所以规则表保守 +
  留"放开一组重问"的回退。
- 工作量约半天（规则表复用 + `_narrow_tools` + 改用例 + 新判据 + live 对照测量）。

## 3. Hook 注册表（最小版）—— 状态：`未拍板`

**决策记录（2026-09-22）**：涉及"模型能做什么"的策略，本项目选 **能力不可得**路线（敏感工具不注入、
写方法在对象上不存在、执行前硬闸），而不是 hook / 拦截器路线 —— 拦截依赖"检查点没被绕过 +
注册顺序 + 没人返回 allow"，能力不可得没有这些前提。代价：新增策略要改核心循环、不可多租户；
参数级语义检查（如"这条 SQL 是不是只读"）目前也没有挂点。真要支持企业策略，按本节的
"最小实现 + 不变式"来，**并先把不变式用测试钉住再动代码**（不变式的钉子见
`tests/test_readonly.py` 的"复合保证"一节）。

**动机（来自一个真实形态：数据分析 agent）**

- `PreToolUse` 检查 SQL 是否只读（拒绝写语句 / 多语句 / `ATTACH` / `PRAGMA` 写 / 危险函数）；
- `PostToolUse` 对结果脱敏（PII 列在进入模型上下文之前处理掉）。

这类需求不适合写进核心循环：**策略会变、检查项会加**，而循环应该是稳定核心（扩展挂在循环上，
不写进循环里）。但它与我们已宣称的结构性保证有直接冲突，所以先把不变式定下来，再决定做不做。

**必须成立的不变式（否则不做）**

1. **hook 只能收紧，不能放开**（对齐 CC 的 `settings.json` deny > hook allow）：所有 hook 跑完之后，
   档位闸 / 记忆写闸 / 只读门面照样执行；hook 的返回值里**没有 allow** 这一档。
2. **fail-closed**：解析失败 / hook 抛异常 → 按拒绝处理，绝不"检查失败就放行"。
3. **单一出口**：PostToolUse 若改写结果，**同一份改写后的结果**同时用于 ①进模型上下文、
   ②落审计、③`done` 事件 —— 不允许"给模型脱敏、给日志原文"或反之，否则 `grounded` 的证据链断裂。
4. **源头最小化优先于事后脱敏**：能"不查 / 不返回"的字段就不要"查出来再洗"。我们已有先例：
   `get_process_identity` 的完整路径在聚合档**根本不产出**，而不是产出后打码。PostToolUse 脱敏
   只做**兜底**，且必须记录 `masked_fields` 让模型知道"这里被脱敏了"（否则它会以为数据缺失而乱猜）。

**最小实现（如果做）**

- 只做 3 个事件：`PreToolUse`（回调只能返回 `deny(reason)` 或 `None`）、`PostToolUse`（只读通知 +
  可选改写）、`Stop`（只能返回"再补一轮"，次数由系统固定上限 —— 同 Claude Code 的 `stopHookActive` 防死循环）；
- `assistant.register_hook(event, cb)` 只对**进程内代码**开放，不开放给外部插件（插件会顺带拿到写能力）；
- 迁移顺序：先把现有 4 类硬编码扩展点**等价**搬进 hook（行为不变，evals 全绿），再谈新增能力；
  顺序反了就是"边重构边加功能"。

**前置条件（先做这个，约 20 分钟）**

一条不变式测试：**"注册一个想放行的 hook，聚合档仍然执行不了明细工具"** —— 不需要真引入注册表，
也能先把边界钉住（现成的 `injection-capability-01` 就是它的雏形）。
